# 端侧视觉值守系统 · 白皮书正文（第 1–6 章）

> 平台：CIX P1（CD8180，12 核 Cortex-A720/A520）+ 天数 MR-V100 32GB + Arm China NPU（X2_1204MP3，45 TOPS）
> 整机功耗约 18 W，全离线运行
> 数据截止：2026-11-23，全部为板卡实测

---

## 一、背景

### 1.1 场景

建筑工地、产业园区、洁净车间这类现场，真正的安全需求往往不是"识别更多类别"，而是**守住一小块地方**：塔吊吊装禁区不许进人、临边区域靠近要告警、洁净室必须按着装进入、有限空间作业必须有人监护。这类需求的共同点是：

- **规则经常变**：今天守吊装区，明天改成临边，后天要加"必须戴安全帽"；
- **现场没有网络**：工地临时用电、园区内网隔离，云端方案既传不上去也不允许传；
- **没有机房**：只有一台挂在弱电箱里的边缘盒子，供电、散热、成本都受限；
- **要能追责**：报警之后必须能回答"几点进的、待了多久、几个人、有没有戴安全帽"。

### 1.2 技术路线的变化

传统做法是训练一个闭集检测器（安全帽、反光衣、人），规则用坐标硬编码。它的问题是**每加一条规则就要重新标注、重训、重部署**，在现场根本跟不上。

近年出现的**指代式检测（referring detection）**改变了这一点：模型接受一句自然语言描述（"穿蓝色衣服的人"、"正在爬梯子的人"），直接输出符合描述的所有目标框。代表性工作是 IDEA 的 **RexSeek-3B**（ICCV 2025）——它把指代任务转成"检索"：先用人体检测器给出候选框，再让多模态大模型从候选里挑出符合描述的那几个。

对端侧产品而言，这条路线带来两个直接好处：**改一条规则只需要改一句话**；**复合条件（区域 + 装备 + 人数 + 时长）可以在 Agent 层组合**，不需要新模型。

代价是算力：RexSeek 的视觉前端是 CLIP-L/14-336 + ConvNeXt-L@768 双塔，加上 3B 的 Qwen 解码器；如果检测器也放在 GPU 上，单帧延迟会超过 300 ms，而且检测器与双塔会抢同一张卡。

### 1.3 硬件形态与约束

本系统跑在一颗国产 SoC 上，算力是三块异构单元：

| 单元 | 规格 | 擅长 | 短板 |
|---|---|---|---|
| CPU | 12 核（8×A720 + 4×A520） | 预处理、图像编解码、业务逻辑 | 推理慢，无向量加速 |
| NPU | Arm China X2_1204MP3，45 TOPS INT8 | 卷积网络、大 batch 定点推理 | 不支持动态 shape / 文本；编译器对混合取值范围敏感 |
| GPU | 天数 MR-V100，32 GB，bf16 峰值 51.6 TFLOPS / 573 GB/s | Transformer、大模型解码 | 与视觉塔共享，容易被抢占 |

三条硬约束贯穿全文：**无外网**（模型、词表、证据全本地）；**功耗 18 W**（不能长时间满载）；**无 Triton**（板端 PyTorch 无法 `torch.compile`，只能靠 CUDA Graph 与推理框架自带优化）。

## 二、问题

### 2.1 目标

在单台边缘盒子上，同时满足：

1. **精度**：开放词表指代任务上，端到端精度不低于官方 RexSeek 的同规模水平；
2. **速度**：单帧端到端不高于 250 ms（4 FPS 以上），保证一路视频按 0.5× 回放、每 2 秒抽帧不丢帧；
3. **可离线、可追溯**：全链路本地，事件可回放、可追问。

### 2.2 两条既有路线都不成立

**路线 A：官方 RexSeek-3B + Grounding DINO + L 塔（全 GPU）**

这是精度参考线，板端实测：

| 段 | 耗时 |
|---|---:|
| 前处理 | 42.6 ms |
| Grounding DINO（graft448，GPU） | 92.6 ms |
| CLIP-L/14-336 + ConvNeXt-L@768（GPU） | 89.4 ms |
| Qwen2.5-3B（vLLM + CUDA Graph） | 78.5 ms |
| **端到端关键路径** | **303.4 ms** |

精度（HumanRef 6 域分层 120 条）：F1@0.5 = **0.7475**。

问题在于**检测器与双塔都在 GPU 上，无法重叠**：DINO 的 92.6 ms 是纯串行开销。这直接吃掉 4 FPS 目标。

**路线 B：v1（Grounding DINO + ViT-B + ConvNeXt-B）**

这是此前的中间方案：把视觉塔换成 B 规模、ConvNeXt-B 放 NPU，GPU 只跑 DINO 与 ViT-B。板端实测端到端 **216.2 ms**，达标；但精度只有 **F1@0.5 = 0.6459**，比路线 A 低 10 个点，且短板集中在 interaction（0.327）与 reasoning（0.498）这两类最需要语言理解的表达上。

**B 塔省下了算力，也省掉了理解能力。**

### 2.3 核心矛盾

把两条路线摊开看，矛盾非常具体：

- **候选生成（person 检测）** 是纯卷积任务，NPU 最擅长，放 GPU 是浪费；
- **语言选择（RexSeek 的检索式解码）** 需要 Transformer 与 3B 解码，只能在 GPU；
- 现有方案里，检测器要么跟着双塔挤 GPU（路线 A，+92.6 ms 串行），要么退化视觉塔来腾空间（路线 B，−10 点精度）。

于是问题被定义为：

> **能否把"person 候选生成"整体迁到 NPU（且不损失候选质量），把 GPU 完整留给视觉塔与语言模型，从而在 ≤250 ms 内拿到接近路线 A 的精度？**

这个问题有两个技术难点，也是本文的主要工作：

1. **NPU 侧**：开放词表检测器 YOLOE-26l 的分类打分分支在导出/编译后会变成全 0（文本嵌入没有烘进图里；混合取值范围的输出张量被单一 INT8 scale 压平）。必须重新导出并拆分输出，NPU 才能给出可用的 person 置信度。
2. **系统侧**：检测与双塔在不同单元上必须真正并行，且 LLM 从 HF `generate` 换成 vLLM + CUDA Graph（21× 差异），否则端到端仍被语言模型拖死。

## 三、异构算力设计

### 3.1 总体切分

| 单元 | 承担 | 实测耗时 |
|---|---|---:|
| CPU | letterbox 640、768 双路归一化、框编码、分词 | 39.4 ms |
| **NPU（INT8）** | **person 候选生成（YOLOE-26l）** | **51.7 ms** |
| GPU（bf16） | CLIP-L/14-336（28.1 ms）+ ConvNeXt-L@768（61.3 ms） | 89.4 ms |
| GPU（bf16） | Qwen2.5-3B 检索式解码（vLLM + CUDA Graph） | 78.5 ms |

关键路径 = `39.4 + max(51.7 NPU, 89.4 GPU) + 78.5 = 207.3 ms`。**NPU 的 51.7 ms 完全被 GPU 双塔掩盖**，检测迁移不增加端到端延迟。

### 3.2 目标检测：YOLOE-26l person @ NPU

#### 3.2.1 为什么选 YOLOE，且只用 person 词表

RexSeek 是"检索式"架构：候选质量决定上限，语言模型只负责从候选里挑。因此检测器只需要**把人找全、找准**，不需要理解描述。实测对比（同 120 条，候选召回 @IoU 0.5）：

| 候选源 | 框/图 | 候选召回 |
|---|---:|---:|
| 数据集自带候选（上界） | 7.2 | 0.990 |
| Grounding DINO（person 提示，阈值 0.25） | 8.1 | 0.944 |
| YOLOE-26l（person 词表，NPU INT8） | 10.9 | **0.911** |

词表收缩到 `person` 是关键：YOLOE 原生支持开放词表，但把整句指代表达当提示会显著降低候选召回（复杂描述下 top-6 召回仅 0.83）；而 `person` 单类提示能把召回拉到 0.91，泛化差异交给后面的 3B 模型。

#### 3.2.2 导出：把文本嵌入烘进图

原始导出的 116 通道模型有一个致命问题：**80 个 COCO 类分数全为 0**——因为 YOLOE 的类别分数来自文本嵌入（动态输入），导出时没有固化，分类分支实际是死的。

解决办法是在导出前固定词表：

```python
m = YOLOE("yoloe-26l-seg.pt")
tpe = m.get_text_pe(["person"])          # RepRTA 文本嵌入
m.set_classes(["person"], tpe)           # 固化单类
m.export(format="onnx", imgsz=640, opset=17)
```

导出后的 ONNX 输出变为 **37 通道 = 4 框 + 1 person 置信度 + 32 mask 系数**，分数是真实可用的（0–0.87）。

> 词表生成依赖 `mobileclip2_b.ts` + RepRTA 头 + CLIP 分词器。为在离线环境复现，我们用 HuggingFace `CLIPTokenizer` 对 `mobileclip2_b.ts` 做分词，重建的嵌入与原 `W200.npy` 逐条对齐 **cos = 1.00000**，证明分词与投影链路等价。

#### 3.2.3 编译：INT8 的两个坑

第一版 INT8 编译完成后，NPU 输出的 person 分数**仍然全 0**。定位到编译器的输出张量量化策略：最后的 `Concat` 把框（0–650）、分数（0–1）、mask（−5..5）拼成一个 37 通道张量，被赋予了**单一 per-tensor INT8 scale（0.1946）**，分数被压到 0。改对称/非对称量化都无效。

两种可行修法：

| 方案 | 结果 | 精度 | 延迟 |
|---|---|---:|---:|
| 让该 `Concat` 留在 fp16（`trigger_float_op = disable & <[Concat]:float16_preferred!>`） | 分数正常 | 0.7273 | 49.9 ms |
| **把输出拆成 `box` / `score` / `mask` 三个独立张量**（推荐） | 分数正常，且每个输出独立 scale | **0.7468** | 51.7 ms |
| 混排 Concat 全 INT8（对称/非对称） | 分数恒为 0，不可用 | — | 42.5 ms |

最终采用**拆分输出 + 全 INT8**。它比 fp16 方案精度高 2 个点（框和分数各自量化，框也变紧了），延迟只多 1.8 ms（4 个输出张量的搬运）。

#### 3.2.4 标定

- 输入：letterbox 640（pad 114），RGB，/255；
- 阈值：`score ≥ 0.25`，NMS IoU 0.7，不设上限（平均 10.9 框/图）；
- 注意：同一 ONNX 在 onnxruntime/IxRT 上跑时最优阈值是 0.05–0.10（0.25 只有 0.645），**阈值必须按设备标定一次**。

### 3.3 Agent 设计

#### 3.3.1 为什么是"检索式"而不是"生成式"

如果让 3B 模型直接输出坐标（生成式），端侧有两个不可接受的问题：坐标回归精度差、幻觉无法约束。RexSeek 的思路是把指代变成**索引选择**：候选框由检测器给出（几何精度由检测器保证），模型只输出 `<obj3>` 这样的索引。我们的 Agent 完全建立在这个约束上：

```
图像 → person 候选（NPU）→ RexSeek 双塔 + Qwen（GPU）→ <objN> 索引 → 候选框
```

这样模型再怎么"想错"，也只能选错候选，不会凭空造框；框的质量与检测器绑定，可测、可回归。

#### 3.3.2 能力层：工具而非提示词

Agent 不是"一个万能 prompt"，而是一组**可组合的工具**，每个工具对应一类现场提问：

| 工具 | 作用 | 依赖 |
|---|---|---|
| `ground` | 按描述定位目标（"穿蓝色衣服的人在哪"） | RexSeek 检索 |
| `count` | 计数 | 候选 + 区域 |
| `zone_query` | 开放描述 + 区域归属（"他进没进危险区"） | `ground` + 多边形判定 |
| `ppe_check` | 装备检测（安全帽、反光背心） | 按需 open-vocab 检测 |
| `attribute` | 反向属性（"这个人穿什么颜色"） | 多假设定位 + IoU 匹配 |
| `guard_check` / `guard_events` / `guard_segment` | 实时区域状态 / 台账 / 整段统计 | 事件库 |

两个设计要点：

- **不在值守时自动标注所有属性**。值守只跑 person，其他属性（安全帽、颜色）只在用户提问时按需检测一次，避免每帧都付出额外算力；
- **事实与语言分离**。时间、人数、时长这类事实由事件库直接拼装回答，不经过模型；只有开放式问题（"有什么风险"）才交给 Qwen 组织语言。这样数字不会错、时间不会编。

#### 3.3.3 决策层：规则护栏 + 小模型 planner

纯 planner 在小模型上不稳定（会拿台账统计去回答"戴没戴安全帽"），纯规则又无法覆盖开放问法。最终是**规则护栏 + planner 决策**：

- 护栏（必须走确定性工具）：台账类 → `guard_events`；装备类 → `ppe_check`；事件统计 → `guard_segment`；区域归属 → `zone_query`；
- 其余交给 Qwen planner 在工具目录里选，失败再退回关键词规则，最后兜底 `ground`；
- trace 里记录 `chosen_by`（Agent 决策 / 规则护栏 / 规则兜底），可解释。

性能上，把 planner 从 CPU 0.8B 换到 GPU 1.5B、提示词 813→350 token、加翻译缓存之后，典型问答从 6.3 s 降到 1.0 s 量级。

#### 3.3.4 事件模型：把"帧"折叠成"事件"

值守台不是逐帧报警，而是维护一张 `guard_episodes` 表：

| 字段 | 含义 |
|---|---|
| `enter_ts` / `exit_ts` / `duration_s` | 进入 / 离开 / 持续 |
| `persons_max` / `persons_total` | 峰值人数 / 跨帧去重人数 |
| `mission` | `danger_zone`（进禁区）/ `duty_zone`（值守区无人） |
| `evidence` / `evidence_last` | 进入 / 离开取证图 |
| `segment` / `n_frames` | 事件片段目录与抽帧数 |

规则：一次"进入→离开"记一条；离开超过 15 秒才回填离开时间（避免人短暂出画把一次事件刷成多条）；事件期间逐帧归档（默认 960 px、最多 300 帧），支持片段回放与整段追问。这一层是"可追溯"的物理基础——所有对话回答都能落到具体事件与帧。

> 架构上仍有一个已知缺口：**v3 的 person 检测器永远会给框，模型不会拒答**。实测 rejection 子集 20 条里只有 1 条输出为空（v1 是 11 条）。目前靠"区域 + 检测为空"的业务规则兜底，属于后续要补的能力。

### 3.4 数据流与延迟预算

```
视频帧 ──CPU 39.4ms──► 640 张量 ──NPU 51.7ms──► person 候选(10.9)
                                            │
                                            ├─► GPU: CLIP-L 28.1 + CN-L 61.3 (89.4ms) ─┐
                                            │                                          ├─► Qwen vLLM 78.5ms ─► <objN>
                                            └─► 候选框编码 / RoI 对齐 ─────────────────┘
关键路径 = 39.4 + max(51.7, 89.4) + 78.5 = 207.3 ms
```

> 图中 max() 只取两项，是因为候选组装（0.4 ms）已计入 NPU 支路：`max(51.7 + 0.4, 89.4) = 89.4`，与上式等价（见 §4.1）。

## 四、推理速度

本章的目标是一个数字：端到端 ≤250 ms（4 FPS）。达到它的路径不是一次设计出来的，而是**两次否决之后收敛**的。4.1 固定基线与口径；4.2–4.4 按迭代顺序给出三次方案及其实测判据（否决两次、成立一次）；4.5 把三次迭代放进同一张表，给出最终方案相对基线的收益分解；4.6 给出这一收益的成立边界；4.7–4.8 补齐尾延迟、吞吐与能效；4.9 汇总。

### 4.1 目标、基线与测量口径

**基线**是全 GPU 串行：Grounding DINO（graft448）+ CLIP-L/14-336 + ConvNeXt-L@768 + Qwen2.5-3B，全部落在 MR-V100 上逐段执行。这是官方 RexSeek 的原始形态，也是本章所有"更快"的参照对象。

| 基线段 | 耗时 (ms) |
|---|---:|
| 前处理（含 DINO 预处理与分词） | 42.6 |
| Grounding DINO | 92.6 |
| CLIP-L/14-336 + ConvNeXt-L@768 | 89.4 |
| Qwen2.5-3B（vLLM + CUDA Graph） | 78.5 |
| **端到端** | **303.4（3.3 FPS）** |

精度参照：该配置 F1@0.5 = **0.7475**（第 5 章表 5.1）。目标是把 303.4 ms 压到 250 ms 以下，同时不显著低于这个精度。

本章所有数字均来自板端单进程实测，口径先于结论固定：

- **同一批图**：HumanRef 6 域分层 120 条（`annot_strat120`），同一进程内逐段打点，每段前后 `sync()`；有效计时 **117 条**（3 条因候选为空提前返回，无耗时记录）。
- **部署口径**：视觉塔走 CUDA Graph，LLM 走 vLLM + CUDA Graph。
- **分项独立测量**：视觉塔与 LLM 单独预热 3–5 次后取 30 次的均值 / 中位 / p90。
- **前处理**不含 JPEG 解码；最终方案的 **NPU 检测段**用外部注入的实测值 51.7 ms（含张量搬运），不参与逐图打点，因此该段在最终部署中为常量。

比较只在三个定义明确的量上做，后文不再混用：

| 指标 | 定义 | 用途 |
|---|---|---|
| 串行和 `T_s` | 各段耗时直接相加，假设全部顺序执行 | 衡量"如果不会重叠"的代价 |
| 关键路径 `T_cp` | `t_prep + max(并行支路) + t_llm` | 端到端延迟 |
| 并行利用率 `η` | `T_s / T_cp` | `η=1` 为纯串行，`η>1` 的部分即被隐藏的工作 |

### 4.2 迭代一：按模块独立性做三路并行（否决）

**动机。** 计算图上三段互不依赖：A = Grounding DINO（只吃原图）、B1 = CLIP ViT-L/14-336（只吃原图）、B2 = ConvNeXt-L@768（只吃原图），它们只在 mm_projector 与 RoI 处汇合（依赖图见 §3.4）。既然没有数据依赖，就可以各占一块算力同时跑：DINO 留 GPU，ViT-L 给核显（Mali-G720，OpenCL），ConvNeXt-L 给 NPU。这是"把算力用满"最直觉的做法。

> 第 1 章只列了最终使用的三类单元；板载另有 Immortalis-G720 核显，只在这一轮评估中出现，最终未采用（原因见本节末）。

**单模块测量。** 三条链路均已在板端跑通，逐模块实测如下。GPU 列为部署管线内实测（含 CUDA Graph）；核显与 NPU 列为裸模型实测、不含管线前后处理——这一口径差异只会使对比更有利于 GPU：

**表 4.1 同一模块在三类单元上的实测耗时（ms）**

| 模块 | GPU MR-V100（bf16/fp16） | 核显 Mali-G720（OpenCL） | NPU X2_1204MP3（INT8） |
|---|---:|---:|---:|
| Grounding DINO（graft448） | 92.6 | 无可用 CV runtime | 不可部署（GridSample / 可变形注意力） |
| CLIP ViT-L/14-336 | 28.1 | 418.6 | 538.7（Fast2D 融合后 465.5） |
| ConvNeXt-L@768 | 61.3 | 800.8（数值不通过） | 346.5（l3 cosine 0.636，数值不通过） |

**判定：更慢。** 按"ViT-L→核显、ConvNeXt-L→NPU、DINO→GPU"这一最佳可行分配，关键路径由最长支路决定：

```
42.6 + max(418.6, 346.5, 92.6) + 78.5 = 539.7 ms   →  1.78× 基线
```

其余两种分配同样不达标：

| 分配 | 关键路径 (ms) | 相对基线 |
|---|---:|---:|
| 只把 ConvNeXt-L 搬 NPU，ViT-L 留 GPU | `42.6 + max(346.5, 92.6+28.1) + 78.5 = 467.6` | 1.54× |
| 把 ViT-L 也搬 NPU（融合后 465.5） | `42.6 + 465.5 + 78.5 = 586.6` | 1.93× |

**否决理由三条，按严重程度排序：**

1. **弱单元对大模型的绝对能力差 6–19 倍。** ViT-L：28.1 → 418.6（核显）／465.5–538.7（NPU）；ConvNeXt-L：61.3 → 346.5（NPU）／800.8（核显）。这三段原本在 GPU 上合计 89.4 ms，拆出去后最慢的一段变成 418.6 ms。
2. **数值不可用。** ConvNeXt-L 在 NPU 上 l3 cosine 只有 0.636（混合取值范围的量化误差，与 §3.2.3 同类），在核显上直接数值不通过；只有 ViT-L 在 NPU 上维持 0.981，但仍慢 16 倍。**即使速度可接受，精度也不可接受。**
3. **工程不可交付。** 核显无通用 CV runtime（板端 MNN Python 绑定要求 glibc 2.38，实际 2.36），418.6 ms 是自建 MNN C++ 推理器换来的，而它的收益上限只有 28.1 ms。

**教训（本章后续都建立在这一条上）：并行不改变 `max()`，它只是把"各段之和"替换成"最慢的那条支路"。** 当被搬走的大模块在新单元上比原来的串行和还长时，`max()` 取到的是一个更大的数——并行变成负收益。本轮里 418.6 与 346.5 都大于基线的 303.4，所以无论怎么分配都更慢。这一轮没有走到端到端联调：单模块测量已经否决了它。

### 4.3 迭代二：缩小视觉塔（速度达标，精度 −10.2）

大模块搬不动，反过来的做法是"让模块变小"：把 L 塔换成 -base 塔（ViT-B/32@512 + ConvNeXt-B/512），塔的计算量降到约 1/3，再让 ConvNeXt-B 落 NPU、ViT-B 留 GPU（即 v1）。

```
39.0 + max(98.7, 78.7) + 78.5 = 216.2 ms   （4.6 FPS）
```

- **速度：达标。** 216.2 ms < 250 ms；且第一次真正用上了 NPU——78.7 ms 的 ConvNeXt-B（含 RoI 与投影）被 GPU 的 98.7 ms 完全掩盖。
- **精度：不可接受。** F1@0.5 = 0.6459，比基线 0.7475 低 **10.2 点**（相对最终方案的 0.7468 则是 10.1 点）。按第 5 章表 5.3 的分解：其中约 **−12.2 点**来自塔从 L 降到 B，另有约 +2.1 点被"改用数据集候选"抵消（v1 的精度用数据集候选，不含检测器误差）。
- **损失位置：** interaction 0.327（基线 0.638）、reasoning 0.498（0.672）、attribute 0.733（0.892）——全部是需要"视觉-语言细对齐"的域。唯一上升的是 position（0.731 vs 0.542），那是候选源带来的，不是塔。

**结论：B 塔省下了算力，也省掉了理解能力。** 这条路线用精度换速度，账不划算。但它留下两条确定的信息，正好划定下一步的搜索空间：

1. **NPU 的可承载上限大约就是 B 规模**：ConvNeXt-B 78.7 ms 能跑，ConvNeXt-L 346.5 ms 不能跑；
2. **精度主要由视觉塔的规模决定**，所以塔不能再动。

### 4.4 迭代三：保留 L 塔，替换检测器（最终方案）

两条信息把问题压缩成一句话：**塔不能缩小、弱单元只能装 B 规模的东西——那么"本来就不需要 L 规模"的模块是哪一个？**

答案是检测器。RexSeek 是检索式架构：候选由检测器给，语义由 L 塔与 3B 完成（§3.3.1）。检测器只需要把人找全，不需要理解"穿蓝衣服""正在爬梯子"。Grounding DINO 的 92.6 ms 里有相当一部分花在文本编码与跨模态融合上，而这部分能力在本系统里是**冗余的**：它所做的语义判断，下游的 L 塔与 3B 会重做一遍，而且做得更好。

**动作：** 把 GD 换成 YOLOE-26l，词表固定为 `person`，INT8 部署到 NPU。

- 单类头烘焙后只有 37 通道输出（4 框 + 1 分数 + 32 mask 系数），模型 23.4 MB（§3.2.2–3.2.3）；
- 实测 51.7 ms（含搬运），加候选组装 52.1 ms；
- 候选召回 0.911（§3.2.1），足以支撑 3B 的检索。

```
39.4 + max(52.1, 89.4) + 78.5 = 207.3 ms   （4.8 FPS，F1@0.5 = 0.7468）
```

**为什么这次成立，三个条件缺一不可：**

1. **它够小**：`52.1 < 89.4`，所以被完全掩盖（判定条件见 4.6）；
2. **它缩小不损语义**：单类检测只做"找出所有行人"，省掉的语义负载恰好由必须保留的 L 塔与 3B 承担——这是检索式架构的红利；
3. **它腾出了 GPU**：检测器离开 GPU 后，GPU 的 89.4 ms 全部用于 L 塔。作为对比，迭代二的 GPU 98.7 ms 里有 93.8% 花在 DINO 上，塔只分到 6.1 ms。

三段迭代合起来给出一条比"异构"更准确的判据：**可迁移的模块必须同时满足"小"与"语义廉价"。** 迭代一满足"语义廉价"（DINO 本身在 GPU 上跑得很好）却不满足"小"；迭代二满足了"小"，但缩小的是语义最贵的模块；只有迭代三两项都满足。

### 4.5 三次迭代对比与收益分解

**表 4.2 三次迭代（同一测量口径下的三个方案）**

| 阶段 | 方案 | 关键路径 | FPS | F1@0.5 | 判定 |
|---|---|---:|---:|---:|---|
| 基线 | 全 GPU 串行（GD + L 塔） | 303.4 | 3.3 | 0.7475 | — |
| 迭代一 | L 塔拆到核显/NPU（最佳分配） | 539.7 | 1.9 | 数值不合格 | ✗ 更慢 1.78× |
| 迭代二 | 换 B 塔（DINO + ViT-B + CN-B@NPU） | 216.2 | 4.6 | 0.6459 | ✗ 精度 −10.2 |
| **迭代三** | **保留 L 塔，GD→YOLOE@NPU** | **207.3** | **4.8** | **0.7468** | **✓** |

如表 4.2 所示，最终方案相对基线：**端到端 303.4 → 207.3 ms（−96.1 ms，1.46×），帧率 3.3 → 4.8 FPS，F1@0.5 差 −0.07 点**（统计上不可分辨，见第 5 章 5.4）；相对当时唯一达标的迭代二：**再快 8.9 ms，且精度高 10.1 点**。第三次迭代同时优于基线与前两次尝试，没有在速度与精度之间做折中。

收益如何归属？把 96.1 ms 拆成两个动作——换前端（GD→YOLOE-person）与换单元（GPU→NPU，含重叠）——它们**不可加**，因为第二个动作同时改变了第一个动作的计价方式：

**表 4.3 收益归因（A/C 为实测口径，B 为推算）**

| 配置 | 检测落点 | 执行方式 | 关键路径 | 相对基线 |
|---|---|---|---:|---:|
| A 基线（GD + L 塔） | GPU | 串行 | 303.4 | — |
| B YOLOE + L 塔（检测仍在 GPU）※ | GPU | 串行 | 217.5 | −85.9 |
| C YOLOE + L 塔（检测在 NPU，串行执行） | NPU | 串行 | 259.4 | −44.0 |
| **D 最终方案** | NPU | **重叠** | **207.3** | **−96.1** |

※ B 为推算：检测段取实测的 9.8 ms（YOLOE-26l，IxRT fp16），其余各段取表 4.5 的实测值。该组合未做端到端实测。

两条归因路径给出不同分配：

| 路径 | 第一步 | 第二步 | 合计 |
|---|---|---:|---:|
| A → B → D | 换前端 **−85.9** | 换单元并重叠 −10.2 | −96.1 |
| A → C → D | 换前端并换到 NPU −44.0 | **重叠 −52.1** | −96.1 |

两种说法都对，回答的是不同问题：A→B→D 说"在 GPU 上就该先换前端，换单元只值 10.2 ms"；A→C→D 说"若按 NPU 逐段串行部署，重叠能再省 52.1 ms"。差异的根源是：不存在"只换单元、不换前端"的可行配置——GD 含可变形注意力与动态算子，上不了 NPU。**因此"重叠"不是独立于"异构"的第三个优化项，它是异构的一个后果**：不换单元时，这个选项的取值恒为 0。

**异构买到的到底是什么：GPU 预算的归属。** 换一个视角，看每帧 GPU 时间花在什么地方（不含 LLM，因为三种配置都必须把它放 GPU）：

**表 4.4 GPU 每帧时间的使用（ms）**

| 配置 | GPU：检测器 | GPU：视觉塔 | NPU：被掩盖的项 | 塔规模 | 关键路径 | F1@0.5 |
|---|---:|---:|---|---:|---:|---:|
| 迭代二（v1） | 98.7 | **0** | ConvNeXt-B 78.7 | B | 216.2 | 0.6459 |
| 基线 | 92.6 | 89.4 | — | L | 303.4 | 0.7475 |
| **最终方案** | **0** | **89.4** | person 检测 51.7 | **L** | **207.3** | **0.7468** |

迭代二与最终方案的关键路径只差 8.9 ms，但两者用 GPU 的方式完全相反：**迭代二的 GPU 上没有视觉塔时间——98.7 ms 全部给了检测器，B 塔被放到 NPU（78.7 ms，完全被掩盖）；最终方案反过来，GPU 的 89.4 ms 全部是 L 塔，检测器 51.7 ms 交给 NPU 并同样被掩盖。** 两者都成功隐藏了自己的 NPU 支路，区别在于"被隐藏的是什么"：一个藏塔，一个藏检测器。

> **异构不改变任何单段的耗时，它改变哪一段占用关键资源。** NPU 的作用不是把检测做得更快（同一模型它慢 5.3 倍），而是让检测**不再消耗关键路径上的 GPU 时间**，从而把这部分预算整体让给视觉塔的规模。

这也解释了为什么在检测迁走之后没有选更小的塔：预算已经腾出来了。

### 4.6 判定条件与失效边界

4.4 节的结论有一个可以被证伪的形式。设检测在 NPU 上的耗时为 `D`、双塔在 GPU 上的耗时为 `V`、前处理与 LLM 为 `P` / `L`，则

```
检测放 NPU：T_cp = P + max(D, V) + L
检测放 GPU：T_cp = P + (D_gpu + V) + L        （同卡无法重叠）
```

两式相减，凡 `D ≤ V`，前者恒优，且**优势量等于 `D_gpu`，与 NPU 快慢无关**；即使 `D` 略大于 `V`，只要 `D < D_gpu + V` 仍占优。代入实测值：

- 当前 `D = 51.7`，`V = 89.4`，**余量 37.7 ms——NPU 检测可以再慢 73%，端到端不变**；
- 盈亏平衡点 `D* = D_gpu + V = 9.8 + 89.4 = 99.2 ms`，即 NPU 慢到现在的 1.92 倍才与 GPU 方案打平。

这条判据同时解释了迭代一为什么失败：把 ConvNeXt-L（346.5）或 ViT-L（465.5–538.7）搬到弱单元时，`D` 不但没有小于 `V`，反而大于整个基线（303.4），`max()` 立刻取到它。**异构放置是否值得，只看 `V`，不看 `D`。** NPU 单看推理速度全面劣于 GPU（同一 YOLOE-26l，NPU 51.7 ms vs GPU IxRT fp16 9.8 ms，慢 5.3 倍），系统层面却仍然值得放 NPU——因为 51.7 小于 89.4，而 9.8 只能加在 89.4 的前面。

还有一个前提必须交代：**重叠只能在跨设备上发生。** 同卡并发实测 0.97×（RTX 4060，双塔串行 82.4 ms vs 双 CUDA stream 84.7 ms），原因是两个 kernel 都是算力密集型、会把 SM 占满；MR-V100 只有 12 个 SM，情况只会更差。因此"全 GPU 方案也能靠多流重叠"这一设想不成立：不是没有优化，而是这块硬件上没有这个优化项。

除此之外，还有三个边界：

**（1）双塔耗时 `V` 的边界。** 若补上 Triton/inductor，`V` 预计降到约 56 ms（本板缺 Triton，此为按同模型的编译收益外推），此时 `T_cp = 39.4 + 56 + 78.5 = 173.9 ms`，而检测余量只剩 `56 − 51.7 = 4.3 ms`。换句话说，**GPU 越快，异构的"隐藏"价值越小**；当 `V` 降到 51.7 ms 以下，检测就会重新进入关键路径，此时应优先优化检测而不是双塔。**"被掩盖"将从"结构性"变为"恰好"。**

**（2）LLM 输出长度的边界。** LLM 段的成本结构是 `42.65 + (T−1) × 17.92`（prefill 629 token 42.65 ms，单 token 解码 17.92 ms）。输出越长，这项越贵：

| 输出 token 数 T | LLM 段 | 关键路径 | 相对 250 ms 预算 |
|---:|---:|---:|---|
| 1 | 42.7 | 171.5 | −78.5 |
| **3（当前）** | **78.5** | **207.3** | **−42.7** |
| 5 | 114.3 | 243.1 | −6.9 |
| 6 | 132.3 | 261.0 | **+11.0** |

这张表解释了检索式架构的第二个好处：模型只输出 `<objN>` 索引，输出长度与目标个数成正比而与框的精度无关，**当前平均 3 个 token 就把答案说完**。若改为逐坐标生成（每框 4 个坐标 + 分隔，约 5–6 个 token），单框成本即从 1 token 涨到 5–6 token，按上表插值，两框就会越过 250 ms 预算。**"检索式"不是一个精度选择，它同时是一个延迟选择。**

**（3）候选数对成本的影响可以忽略。** 每个候选在提示里只占 2 个 token（`<objK>` + 特征占位），11 个候选合计 22 token，占 629 的 3.5%。即使候选翻四倍到 44 个（+66 token，+10.5%），按 prefill 的平均单价 0.068 ms/token 估算仅增加约 4.5 ms（+5.7%）。这从成本侧解释了为什么"多给候选、让语言层去挑"是可行的：**候选生成与候选筛选都是廉价环节，昂贵的是视觉塔与解码**。

### 4.7 分阶段实测与尾延迟

**表 4.5 部署配置分段（单位 ms，n=117，120 张同批图）**

| 段 | 配置 | 均值 | 中位 | p90 |
|---|---|---:|---:|---:|
| 前处理 | letterbox 640 + 768 双路 + 框编码 + 分词 | 39.4 | 38.7 | 44.4 |
| **检测** | YOLOE-26l person，NPU INT8，含搬运 | **51.7** | 51.7 | 51.7 |
| NMS + 候选组装 | top-6~all，IoU 0.7 | 0.4 | 0.3 | 0.7 |
| 视觉塔 1 | CLIP-L/14-336，bf16，CUDA Graph | 28.1 | 28.1 | 28.2 |
| 视觉塔 2 | ConvNeXt-L@768，bf16，CUDA Graph | 61.3 | 61.3 | 61.6 |
| **LLM** | Qwen2.5-3B，vLLM + CUDA Graph，629→3 token | **78.5** | 78.0 | 80.8 |
| **关键路径** | `39.4 + max(52.1, 89.4) + 78.5` | **207.3** | 206.6 | 212.3 |

这张表有三处值得单独读。

**其一，"慢段"与"长段"不是一回事。** 视觉塔合计 89.4 ms，是单段最长；LLM 78.5 ms 次之；NPU 检测 51.7 ms 只排第三。若按"各段耗时排序"去优化，第一目标应是双塔；但 4.4 节说明，真正被优化掉的是排序第三的检测段——因为它不在关键路径上。

**其二，分布的形状比均值更说明问题。** 双塔的 p90 与均值只差 0.1–0.2 ms（≤0.4%），LLM 在 vLLM 下 p90 与中位之比为 1.036，检测段为常量；**唯一有实质方差的是前处理**：标准差 13.3 ms、p99 55.3 ms、极值 170.7 ms。这意味着部署后系统的抖动几乎全部来自 CPU 侧的图像处理，而不是来自模型推理。

**其三，前处理均值 39.4 ms 已占关键路径的 19.0%。** 这一比例在下一版硬件上会上升而不是下降：双塔与 LLM 都还有优化手段，letterbox 与归一化则是固定工作。

均值与 p90 不足以描述一个 7×24 值守系统的可用性。按 4.1 的口径逐图合成关键路径 `T_cp,i = t_prep,i + 89.4 + 78.5`：

**表 4.6 关键路径的分布（逐图合成，n=117）**

| 统计量 | 关键路径 (ms) | 前处理 (ms) |
|---|---:|---:|
| 均值 | 207.3 | 39.4 |
| 中位 | 206.6 | 38.7 |
| p90 | 212.3 | 44.4 |
| p99 | 223.2 | 55.3 |
| 最大 | 338.6 | 170.7 |
| 超过 250 ms 的比例 | **1/117（0.85%）** | — |

三点读法：

1. **p99 = 223.2 ms，距 250 ms 预算尚有 26.8 ms 余量**，满足"每 2 秒抽帧不丢帧"的要求；
2. **唯一越界的 1 帧（338.6 ms）由前处理 170.7 ms 造成**，与 NPU、GPU 无关——这是单张图解码/缩放路径上的离群，不是算力问题；
3. 由于关键路径其余各项在本批中为常量，`Var(T_cp) = Var(t_prep)`：**部署后系统的全部抖动都来自 CPU 预处理**。这决定了下一步的优化对象是解码线程池与预取，而不是任何一段模型推理。

> 需要交代的边界：检测段在本批中是外部注入的常量（§4.1），因此 **NPU 自身的抖动未被本实验覆盖**。"抖动全部来自前处理"这一结论只在"NPU 计时稳定"的前提下成立；要验证它，需要把 NPU 计时接入逐图打点。

作为对照，若 LLM 退回 HF `generate`，同批数据的尾部会恶化一个量级：中位 1455 ms、p90 2171 ms、最大 6499 ms，`(p90−中位)/中位 = 49.2%`；vLLM 下同一比值为 `3.6%`，**尾部相对抖动降到 1/13.7**。对一个"按 2 秒抽帧、事件要能回放"的系统，尾延迟比均值更接近可用性本身，这也是 vLLM 成为部署前提而不仅是加速手段的原因。

### 4.8 吞吐与能效：单帧之外的第二个口径

单帧延迟（4.8 FPS）不是系统的吞吐能力：帧与帧之间可以流水线，稳态吞吐由**最忙的那块设备**决定，而不是由各段之和决定。以每帧设备忙时计算上限 `1 / max(T_GPU, T_NPU, T_CPU)`：

**表 4.7 稳态吞吐上限与多路容量（假设完美流水线、忽略调度开销）**

| 配置 | GPU 每帧忙时 | NPU 每帧忙时 | 吞吐上限 | @0.5 FPS/路 可承载 |
|---|---:|---:|---:|---:|
| **最终方案** | 167.9（塔 89.4 + LLM 78.5） | 51.7 | **5.96 FPS** | **约 11.9 路** |
| B 检测留 GPU（YOLOE + L 塔）※ | 177.7 | 0 | 5.63 FPS | 约 11.3 路 |
| 迭代二（v1） | 177.2 | 78.7（被完全掩盖） | 5.64 FPS | 约 11.3 路 |
| A 基线（GD + L 塔） | 260.5 | 0 | 3.84 FPS | 约 7.7 路 |

※ 推算口径同表 4.3。

三点结论：

1. **异构把 GPU 的每帧用时从 260.5 ms 压到 167.9 ms**，稳态吞吐上限相应从 3.84 提到 5.96 FPS（1.55×）。这一比值比单帧延迟的 1.46× 更大，因为延迟口径里还压着一段无法并行的前处理。
2. 单帧 4.8 FPS 与稳态 5.96 FPS 的差额（1.24×）是流水线可回收的部分，代价是引入帧级队列与一到两帧的启动延迟。值守场景可接受：抽帧周期 2 s，队列深度 3 帧以内即可吸收 4.7 节讨论的尾部。
3. 若按整机 18 W 折算，每帧能耗从 5.46 J（A）降到 3.73 J（D），**−31.7%**。这是推算值：它假设两种配置的瞬时功率相同，而 A 配置的 GPU 满载时间更长、实际功耗应更高，故此处的 31.7% 是下界而非上界。

### 4.9 小结：速度账

**表 4.8 优化项与收益**

| 优化 | 前 | 后 | 收益 |
|---|---:|---:|---:|
| LLM：HF `generate` → vLLM + CUDA Graph | 1651.8 ms | **78.5 ms** | **21×** |
| 双塔：eager → CUDA Graph | 96.0 ms | **89.4 ms** | 1.07×（CLIP 1.20×，ConvNeXt 1.02×） |
| 检测器本身：GD（GPU）→ YOLOE（NPU） | 92.6 ms | **51.7 ms** | 1.79× |
| 检测移出关键路径（异构重叠） | 52.1 ms 串行 | **0 ms 额外** | 关键路径 −52.1 ms |
| **端到端** | **303.4 ms** | **207.3 ms** | **1.46×** |

三点说明，按收益排序：

1. **LLM 是最大单项，且是唯一"不做就出局"的优化。** 占关键路径 37.9%；没有 vLLM，端到端是 1.7 s 量级，其余优化全部失去意义。
2. **视觉塔已接近物理上限。** ConvNeXt-L@768 约 41 TFLOPS，达 bf16 峰值 79%；CUDA Graph 只带来 1.02×。CLIP 受启动开销影响更大，graph 给到 1.20×。本板无法 `torch.compile`（`torch._inductor` 需要 Triton），若补上，双塔可降到约 56 ms，端到端可到 **约 174 ms**——这是目前唯一还有明显空间的环节。
3. **异构的价值不能用"快了几倍"概括。** 相对全 GPU 路线 A，端到端 1.46×（207.3 vs 303.4）；相对"同一前端留在 GPU"的反事实，只快 10.2 ms（207.3 vs 217.5）。异构真正买到的是**把 GPU 预算从检测器手里收回来交给视觉塔**（表 4.4：GPU 检测器 98.7 → 0，塔规模 B → L），以及在流水线口径上把吞吐上限从 3.84 提到 5.96 FPS。

一句话：**速度收益不来自"更快的模型"，而来自"把检测挪出 GPU 关键路径"；它的量级取决于你选哪个反事实，但它的机制只有一个——`max()` 取的是较长的那一段。**

## 五、推理精度

第 4 章的三次迭代各自对应一笔精度账：迭代一因数值不合格被否决；迭代二速度达标，代价是 −10.2 点；迭代三宣称"保留 L 塔、只换检测器，所以精度不受影响"——而这个"不受影响"必须由数据证明，不能由速度表暗示。本章就做这件事，并把问题收窄为三个：**把检测器迁到 NPU 到底有没有损精度（5.4）**；**如果损了，损在哪个维度（5.6–5.7）**；**这个损失对本系统的业务判据意味着什么（5.10）**。5.1–5.3 先固定口径与统计分辨率——在 120 条样本上，任何小于 5 点的差异都不可分辨，这一点必须在读表之前就成立。

### 5.1 评测协议

| 项 | 取值 |
|---|---|
| 数据 | HumanRef Benchmark，**6 域各 20 条 = 120 条**（图片来自 `bench/imgs`）；172 个 GT 框，**1.43 个 GT/ref**（120 条口径；100 条计分口径为 1.72） |
| 计分 | 5 个 grounding 域共 **100 条**（172 个 GT）；rejection 20 条单列"正确拒答" |
| 指标 | R/P 逐条平均；`F1 = 2·R̄·P̄/(R̄+P̄)`；严格指标为 IoU 0.5:0.95（步长 0.05，10 个点）逐点 F1 的平均；"域平均"为 5 域 F1 的算术平均 |
| 候选 | 本系统：YOLOE person（conf 0.25、NMS 0.7、不封顶）；对照：GD person（同阈值）、原生 PyTorch（ultralytics）、数据集候选（≤12/ref） |
| 视觉塔与 LLM | 官方 RexSeek-3B（CLIP-L/14-336 + ConvNeXt-L@768）+ Qwen2.5-3B，`do_sample=False` |
| 说明 | 官方论文用 DensityF1、6000 条、7B 模型，与本文口径不同，只能作趋势参照 |

三处必须写明的口径细节，否则表 5.1 会被误读：

1. **F1 是"两个均值的调和平均"，不是"逐条 F1 的平均"。** 两种算法在条目难度不均时会给出不同结果；本文全程用前者，与官方评测脚本一致。
2. **候选数有两个口径。** 检测脚本口径为 10.9 框/图（§3.2）；评测算子对同一候选集重新做 NMS（IoU 0.7），平均 12.5 框/图。精度只在这份重做 NMS 的候选集上计算，两个数字的差异不影响任何结论，但对外引用时应说明取的是哪一个。
3. **v1 的 LLM 走 `prompt_embeds` 注入、`max_tokens=8`**，本系统走 token 注入。两者权重相同，注入方式不同，该差异未单独量化，是 5.9 节列出的一项效度威胁。

### 5.3 统计分辨率：这 120 条能分辨多大的差异

单点评分没有误差棒，而"相差 0.07 个点"这种量级在 100 条样本上没有任何意义。以条目为重采样单位做配对 bootstrap（B=3000，两次配置在同一次重采样的同一条目上计算，消掉条目难度带来的共同方差）：

**表 5.2 估计的不确定性（100 条计分样本）**

| 配置 | F1@0.5 | bootstrap SE | 95% CI | 与 v3 配对差 | 差值的 95% CI | 逐条 胜/平/负 |
|---|---:|---:|---|---:|---|---|
| **本系统** | 0.7468 | 0.037 | [0.668, 0.816] | — | — | — |
| GD graft448 | 0.7475 | 0.037 | [0.670, 0.816] | +0.0006 | [−0.051, +0.056] | 13 / 70 / 17 |
| stock HF GD | 0.7602 | 0.035 | [0.688, 0.830] | −0.0134 | [−0.073, +0.047] | — |
| annotation 上界 | 0.7681 | 0.037 | [0.693, 0.836] | −0.0213 | [−0.095, +0.056] | — |
| YOLOE 原生 PyTorch | 0.7338 | 0.038 | [0.659, 0.805] | +0.0130 | [−0.030, +0.057] | 13 / 74 / 13 |
| v1 | 0.6459 | 0.043 | [0.563, 0.732] | **+0.1006** | **[+0.014, +0.191]** | 27 / 55 / 18 |

三条推论：

**（1）单点差异的置信区间宽约 ±7.5 点，配对后收到 ±5.3 点。** 配对之所以有效，是因为两次配置面对的是同一批图：难度是共同方差，配对把它消掉。**配对口径下的最小可分辨差异（α=0.05）为 5.35 点，未配对为 7.25 点；要做 80% 功效的检测，配对口径下分辨 5 点需约 234 条、3 点需约 650 条、2 点需约 1460 条。** 因此本表的所有"持平"都必须读作"在 5 点分辨率以下不可分辨"，而不是"相等"。

**（2）只有相对 v1 的差距是统计稳健的。** `+10.06` 点，95% CI 为 `[+1.4, +19.1]`，`P(Δ>0) = 0.99`；逐条看是 27 胜 18 负 55 平。其余三组配对差的区间都跨 0。

**（3）样本量的现实含义：** 每域 20 条时，域级的可分辨差异约 `5.35 × √5 ≈ 12` 点。**5.6 节讨论的分域差异（−6.5、+15.8、−9.5）中，只有 position 的 +15.8 同时超过这个下限且置信区间不含 0**，其余两项只能作指示性结论。这一条限定了本章所有分域论述的强度。

### 5.4 等价性检验：迁到 NPU 有没有损精度

把 5.3 的分辨率用在核心问题上，答案比"持平"更弱、也比"有损"更强：

- **点估计：** 0.7468 vs 0.7475，差 **−0.07 点**，是测量标准误（3.7 点）的 2%。
- **区间：** 配对差 95% CI 为 **[−5.1, +5.6] 点**。也就是说，**"迁到 NPU 导致超过 5.1 点的精度损失"这一假设可以在 95% 置信下被排除**。
- **逐条：** 100 条里 **70 条两配置完全同分**，13 条本系统更好、17 条更差；符号检验 `p = 0.585`，方向不可分辨。

**因此正确的表述是：未观测到可分辨的精度差异（95% 置信下界 −5.1 点）；不能表述为"精度无损"。** 前者是数据支持的，后者需要每域 ≥100 条才有资格说。

作为参照，本系统与"数据集候选 + L 塔"这个上界配置的差为 −2.1 点，CI `[−9.5, +5.6]`——**同样不可分辨**。换言之上界本身也没有被显著触及，这既说明候选质量已接近该口径的天花板，也说明 120 条样本不足以把"接近"证成"达到"。

### 5.5 与 v1 的 10.1 点：是塔的上限，还是候选的代价

迭代二（v1）与迭代三（本系统）差 10.1 点，但两者同时改了三件事：塔规模（B→L）、候选源（数据集候选→自检）、LLM 注入方式。所幸"数据集候选"这一档把候选源固定住了，可以先在**同候选口径**下把"塔"这一项分离出来；注入方式的差异留到 5.9 节讨论。

**表 5.3 精度账（两步替换，逐步收敛到部署配置）**

| 步骤 | 配置 | F1@0.5 | 增量 |
|---|---|---:|---:|
| 起点 | v1：数据集候选 + **B 塔** | 0.6459 | — |
| ① 换塔 | annotation 候选 + **L 塔** | 0.7681 | **+12.2** |
| ② 换候选 | YOLOE-person@NPU + **L 塔**（本系统） | 0.7468 | **−2.1** |
| 合计 | | | **+10.1** |

**结论：10.1 点的收益几乎全部来自视觉塔从 B 升到 L（+12.2 点），自检候选的代价只有 −2.1 点。** 注意第②步的括号：这 −2.1 点里既有"候选从人工框换成检测框"的损失，也有"NPU INT8"的损失，5.7 节会把后者的量级单独估出来。

这条链条还有一个必须交代的旁支：**v1 的 10.1 点差距中，约 8.8 点来自"漏答"，而非"选错"。**

**表 5.4 覆盖率与条件精度**

| 配置 | 覆盖率（有输出的可答题占比） | 条件 F1（仅对有输出的条目） | 全量 F1 | 拒答正确 |
|---|---:|---:|---:|---:|
| **本系统** | **0.98** | **0.7621** | **0.7468** | 1/20 |

| annotation 上界 | 1.00 | 0.7681 | 0.7681 | 0/20 |

v1 在 100 条**有答案**的题上有 12 条输出为空（覆盖率 0.88），这 12 条直接计 0。剔除它们后 v1 的条件 F1 是 0.7340，与本系统的 0.7621 只差 2.8 点。于是 10.1 点可以精确分解为：

```
+10.1 = +8.8（v1 的 12% 漏答被补齐）
        +2.8（条件精度更高）
        −1.5（本系统自身 2% 的漏答）
```

**这改变了 v1 的画像：它不是"更准但更少"，而是"更少、且并不更准"。** 而 v1 之所以"更少"，与它 11/20 的拒答正确率是同一个机制——见 5.8。这也顺带说明为什么不能用"拒答率"单独给模型打分：一个把所有题都拒掉的模型，拒答率是 100%。

主表的"持平"是聚合结果。把域拆开，两个前端的能力分布并不相同：

**（2）只有 position 的领先是统计稳健的。** +15.8 点，CI `[+0.8, +31.7]` 不含 0，且超过 §5.3 给出的域级分辨率（约 12 点）；attribute（−6.5）与 interaction（−9.5）的 `P(Δ>0)` 为 0.03，区间刚跨 0，只能作指示。

**（3）这里必须撤回一个此前写在本文里的解释。** 早稿把 position 的下降（相对 v1 −3.1）归因于"本系统候选更多、模型在密集人群中被邻近候选干扰"。该解释与数据不符：

- 逐条相关系数 `corr(n_cand, F1) = +0.12`——候选越多，F1 略高而不是更低；
- 按候选数分箱（0–7 / 8–11 / 12–19 / ≥20 框），F1 为 0.763 / 0.631 / 0.808 / 0.853，非单调，不存在"越多越差"；
- **position 恰好是候选数最少的域（平均 6.7 框/图，其余域 10.5–13.8）**，若"候选多则干扰"成立，它本应是本系统表现最好的域之一。

正确的读法应从表 5.6 的误差结构找：position 上本系统命中 19/25、GD 只命中 16/25 而误报 12 个框——**GD 在该域不是找不到，是选错了人**（其匹配框条件 IoU 高达 0.942，几何很好）；相对 v1 的 −3.1 点则与候选层有关：v1 用的是数据集候选（候选召回按构造为 1.000），本系统用自检候选（召回 0.911），position 类查询（小目标、人群边缘）对候选召回的敏感度最高。

两条结构性事实：

1. **几何紧度是全域、均匀地差 8–12 点**（条件 IoU：0.797–0.873 vs 0.902–0.956），不是某个域的局部故障。这指向候选框的量化/回归精度，而不是某个域的数据分布。
2. **reasoning 是"过度选择"最严重的域：49 个 GT 输出了 103 个框（2.10 个框/GT），其中 59 个不与任何 GT 匹配。** GD 在同一域同样过度选择（85 个框、45 个误报）。**两个前端、同一模型都犯同一个错，说明这是语言层的选择行为，不是候选层的性质**——这也是 reasoning 上两者 F1 几乎相同（0.673 vs 0.672）的原因。

### 5.7 几何精度：量化损伤落在哪一维

严格指标（IoU 0.5:0.95）给出与主表相反的排序：本系统 0.5350，v1 0.6453，GD 0.6885。这个反向是本系统最实在的短板，值得逐层拆开。

**表 5.7 IoU 阈值扫描（F1，100 条）**

| 配置 | 0.50 | 0.60 | 0.70 | 0.75 | 0.80 | 0.85 | 0.90 | 0.95 | 均值 0.5:0.95 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| **本系统** | 0.747 | 0.717 | **0.645** | 0.609 | 0.535 | 0.407 | 0.226 | 0.048 | **0.5350** |
| GD graft448 | 0.747 | 0.733 | **0.709** | 0.694 | 0.686 | 0.658 | 0.620 | 0.566 | 0.6885 |
| YOLOE 原生 PyTorch | 0.734 | 0.719 | 0.703 | 0.685 | 0.663 | 0.623 | 0.573 | 0.465 | 0.6601 |
| v1 | 0.646 | 0.645 | **0.645** | 0.645 | 0.645 | 0.645 | 0.645 | 0.645 | 0.6453 |
| annotation 上界 | 0.768 | 0.768 | 0.768 | 0.766 | 0.766 | 0.766 | 0.766 | 0.766 | 0.7669 |

**（1）本系统与 v1 的曲线在 IoU ≈ 0.70 处交叉。** 0.5 时本系统领先 10.1 点，0.70 时打平，0.75 起被反超，0.90 时落后 41.9 点（0.226 vs 0.645）。**"IoU 0.5 够用、0.75 不够"不是修辞，是这条曲线的斜率。**

**（2）v1 的曲线是平的——因为它没有检测器。** v1 的候选直接取自数据集（`candidate_boxes`），与被评测的 GT 同源，匹配上时 IoU 恒为 1.000。因此 **v1 的严格指标几乎等于 0.5 指标（0.6453 vs 0.6459），它度量的是"塔与 LLM 的选择能力"，完全不含候选框误差。** 这一点决定了"严格指标对比"的正确用法：它是**前端候选质量**的指标，不是模型能力的指标；用它比较本系统与 v1，比较的是"自检候选 vs 人工候选"，不是"两个模型"。

**（3）把"设备"这一变量单独隔离出来。** 表 5.7 里 YOLOE 原生 PyTorch 与本系统是**同一份权重、同一套单类 person 词表**，只是执行路径不同（GPU fp32/ultralytics vs NPU INT8/拆分输出）。两者对照：

**表 5.8 候选框几何（172 个 GT）**

| 配置 | 全 GT 均值 IoU | 中位 | ≥0.75 | ≥0.90 | 条件均值 | 条件中位 | 条件 ≥0.90 | 中心偏移 | 面积比 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| **本系统（NPU INT8）** | 0.629 | 0.809 | 60.5% | **18.6%** | 0.828 | 0.853 | **25.4%** | 2.9% | 0.99 |
| YOLOE 原生（GPU） | 0.697 | 0.917 | 66.9% | 54.1% | 0.908 | 0.955 | 72.7% | 0.7% | 0.97 |
| GD graft448 | 0.732 | 0.958 | 69.8% | 60.5% | 0.931 | 0.976 | 79.4% | 0.4% | 1.00 |
| annotation（人工框） | 0.764 | 1.000 | 73.8% | 73.8% | 0.998 | 1.000 | 99.2% | 0.0% | 1.00 |

"中心偏移"为匹配框中心距除以 GT 对角线，"面积比"为匹配框面积除以 GT 面积，均取中位数。

三条独立证据指向同一个结论——**损伤集中在高精度尾部，而不是整体偏移**：

- **条件均值只降 8.0 点（0.908 → 0.828），条件 ≥0.90 的比例却从 72.7% 掉到 25.4%（−47.3 点）。** 若量化误差是系统性的整体放大/缩小或单向平移，两个统计量应当同步下降；实际是一个缓降、一个崩塌。形状更符合"每个边界各自带小扰动"——它把"典型框"留在原地，把"精确框"抹掉了。
- **没有系统偏置：面积比 0.99（≈1），中心偏移 2.9%。** 框既没有被放大（不是把相邻目标吞进来），也没有整体位移（不是坐标映射错位）。三个量互相自洽：对边长 `d` 的框，中心平移 `0.029×1.41d ≈ 4%d` 对应 IoU ≈ `0.96²/(2−0.96²) = 0.855`，与实测的条件中位 IoU 0.853 几乎相同——**中位框的误差几乎全部是纯平移，且幅度只有边长的 4%。**
- **损失的分布不是"整体变差"，而是"精度档位下移"。** 条件 ≥0.75 的比例仍有 82.5%（GPU 路径 89.8%），说明绝大多数框落在 0.75–0.90 这一档；而 ≥0.90 从 72.7% 掉到 25.4%，说明原本"贴着 GT"的那一档被整体拉回到了 0.8 附近。严格指标（0.5–0.95 等权平均）恰好对这一档最敏感，因此掉 12.5 点；IoU 0.5 判据对此不敏感，因此只掉 0.1 点。

由此得到本章最重要的一条归因：**同一份权重，换到 NPU INT8 之后，R 保持不变（0.7627 vs 0.7610）、P 反而略升（0.7317 vs 0.7084），但严格指标掉 12.5 点（0.5350 vs 0.6601）。语义选择能力没有损失，损失全部落在几何这一维。** 这与速度章"检测被掩盖"的结论互为补充：**异构迁移把代价压缩到了一个可测量、可隔离、且与业务判据部分正交的维度上。**

业务上因此有明确的分界：

- **不受影响**：区域归属（点在多边形内）、计数、进入/离开事件、持续时长——这些判据只依赖 IoU ≥ 0.5 与框中心点，中心偏移 2.9% 远小于任何人员尺度；
- **受影响**：需要亚框级几何的需求，如"距临边还有几米""是否贴边作业"——按当前的框抖动，这类判据不可用，需要保留一条 fp16 的框回归旁路，或对候选框做一次精修。

### 5.8 拒答能力：真实缺口，但代价被高估了

rejection 子集 20 条（描述的目标在图中不存在）中，本系统只有 1 条输出为空，v1 有 11 条（55%，与官方 7B 的 54.1 同量级）。这常被读作"v1 会拒答、v3 不会"。数据支持这个事实，但**不支持"v1 因此更强"这个推论**：

- v1 在 100 条**有答案**的题上同样拒答了 12 条（覆盖率 0.88）；本系统只有 2 条（0.98）。
- 也就是说，v1 的 55% 拒答率，与它 12% 的漏答率，是同一个阈值偏差的两端：**它整体偏向"少说"。** 用覆盖率与条件精度两个维度看（表 5.4），v1 是 `(0.88, 0.734)`，本系统是 `(0.98, 0.762)`——前者在"说不说"上更保守，在"说得准不准"上并不更好。

**正确的说法是：本系统的输出阈值偏松，v1 偏紧；单一"拒答率"无法区分"能力"与"偏差"。** 评价这类系统应给出 `(覆盖率, 条件精度)` 的二维点，或一条随阈值变化的曲线，而不是一个拒答数字。

缺口的根因是架构性的：person 检测器永远会给框，模型没有"无候选"这个出路。当前由业务规则兜底（区域内检测为空 → 判定无人），这只是补丁。修复路径有两条：在候选集为空时直接判拒（构成性兜底），或微调模型使其能输出 `<no-obj>`（能力性修复）；后者需要构造负样本，不在本文范围内。

### 5.9 效度威胁

**内部效度**

1. **单次运行，未估计重复方差。** 评测以 `temperature=0` 贪心解码，结果确定，但 GPU 侧的非确定性算子（归约顺序）与 NPU 编译器的调度差异未做重复测量；本文的 bootstrap 只覆盖"条目抽样"这一项方差，不含"运行"方差。
2. **LLM 注入路径不同。** v1 用 `prompt_embeds`、本系统用 token 注入；两者权重相同，但前缀长度与位置编码不同，对精度的影响未单独量化。5.5 节的 +12.2 点塔收益因此带有这一未受控变量。
3. **候选 NMS 口径差异。** 评测算子对候选集重做 NMS（§5.1 第 2 条），与检测脚本自身口径（10.9 vs 12.5 框/图）不完全一致；该差异只影响候选取舍的边际，不改变主表排序。
4. **域标签回填。** 3 条样本在逐图结果中缺少 `domain` 字段（因候选为空提前返回），本文按标注文件回填；若不回填，域平均会被一个空域名污染（该域 F1=0，会把域平均从 0.7462 拉到 0.6327）。

**统计效度**

5. 每域 20 条、总计 100 条计分样本，域级最小可分辨差异约 12 点（§5.3）。**任何小于该值的分域结论都应视为指示性。**

**外部效度**

6. 评测集为 6 域各 20 条的分层子集，域内分布未做与原数据集的比例对齐；对外发布建议每域 ≥100 条。
7. 与官方发表值不可并列：官方为 7B 模型、6000 条、DensityF1（本文为 3B、120 条、调和 F1）。在"数据集候选 + L 塔"这一上界配置下本文复现到 0.7681，与官方同量级，仅可作为"同家族、降规模、换前端"的对照。

**一项外部一致性检验。** 在另一台机器（RTX 3090，1200 条）上以相同模型做过一次候选源对照：GD 的 DF1@0.5 为 0.6652，YOLOE-26l person 为 0.6703，差值 +0.5 点。**这与本文的"两者在 1 点内不可分辨"方向一致**，且说明该结论不是本板 120 条子集的偶然。

### 5.10 小结：精度账

四个问题，四句带证据的回答：

| 问题 | 回答 | 关键证据 |
|---|---|---|
| 迁到 NPU 有没有损精度？ | **未观测到可分辨差异**，可排除 >5.1 点的损失 | 配对差 −0.07 点，CI [−5.1, +5.6]；70% 条目同分；符号检验 p=0.585 |
| 若损了，损在哪一维？ | **只损几何，不损语义** | 同权重换设备：R 0.7627 vs 0.7610、P 0.7317 vs 0.7084；条件 IoU 0.908→0.828，≥0.90 比例 72.7%→25.4% |
| 相对 v1 的 10.1 点从哪来？ | **塔从 B 到 L（+12.2），不是"会拒答"** | 同候选口径 0.6459→0.7681；v1 覆盖率 0.88、条件 F1 0.7340 |
| 对业务判据意味着什么？ | **区域/计数/时长类不受影响；亚框级几何类需要旁路** | 中心偏移 2.9%、面积比 0.99；IoU 0.5 曲线交叉点 0.70 |

把三章串起来看，本系统的精度—速度联合位置是：

```
全 GPU + GD : 303.4 ms / F1 0.7475 / 严格 0.6885
本系统      : 207.3 ms / F1 0.7468 / 严格 0.5350
v1          : 216.2 ms / F1 0.6459 / 严格 0.6453（候选同源，严格值虚高）
```

**它用 0.07 点（不可分辨）的 F1@0.5 换来了 96.1 ms；代价是严格 IoU 上的 15.4 点，而这项代价已定位为"框几何"这一个维度，并被证明与区域/计数/事件类判据正交。** 这不是"没有代价"，而是**代价被限制在一个可以被业务吸收、也可以被单项工程手段（fp16 回归旁路）修复的范围内**——这正是异构迁移能够成立的前提。
